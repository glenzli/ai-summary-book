# 第六章 推理效率与模型服务

训练回答“参数怎样得到”，服务回答“同一组参数怎样在现实机器上持续产生输出”。两者共享模型结构，却面对不同约束：训练关心总计算量和收敛，在线推理还关心首 token 延迟、逐 token 延迟、并发、显存、尾延迟和失败恢复。模型能力不变时，服务设计仍可以把一次回答的成本和等待时间改变一个数量级；服务设计失误也可以让理论上可用的模型无法部署。

本章只讨论模型服务的基本机制。具体一次调用怎样从 token 走到输出留给卷二；概率采样的含义留给卷三。

## 6.1 Prefill 与 Decode 是两种工作负载

对长度为 $T$ 的输入，decoder-only Transformer 先对全部输入 token 做一次前向计算，建立每层的键值缓存；这一步称为 **prefill**。随后模型每次追加一个 token，并利用已有缓存计算下一个 token；这一步称为 **decode**。

两阶段的硬件特征不同：

| 阶段 | 一次处理的 token | 常见瓶颈 | 主要指标 |
| --- | ---: | --- | --- |
| prefill | 整段输入 | 矩阵计算、长序列注意力 | time to first token，TTFT |
| decode | 通常每请求一个新 token | 权重与 KV cache 读取、调度 | time per output token，TPOT |

因此“每秒多少 token”不是完整指标。离线批处理可以用很高吞吐掩盖单请求等待；交互系统则可能有很低平均延迟，却在高并发下出现不可接受的 P99 尾延迟。合格报告至少同时给出输入/输出长度、并发、TTFT、TPOT、端到端延迟、吞吐和失败率。

## 6.2 KV Cache 为什么占用显存

自回归解码若每一步都重新计算全部前缀，会重复做大量工作。KV cache 保存各层已经产生的 key 和 value，使新 token 只需查询旧缓存。忽略对齐和实现常数时，其字节量可近似写成

$$
M_{\mathrm{KV}}
\approx
2LBTH_{\mathrm{kv}}d_h b,
$$

其中 $L$ 是层数，$B$ 是并发序列数，$T$ 是已缓存长度，$H_{\mathrm{kv}}$ 是 KV 头数，$d_h$ 是每头维数，$b$ 是每个元素的字节数，前面的 $2$ 对应 key 与 value。

这个式子直接解释三件工程事实：上下文越长，缓存线性增长；并发越高，缓存线性增长；multi-query attention 或 grouped-query attention 通过减少 KV 头数降低缓存。低精度 KV、分页式内存管理、缓存淘汰和前缀共享则从表示或调度层进一步降低占用。

缓存不是模型的长期记忆。它只是在一次或一组相关调用中保存中间张量；会话结束、缓存回收或模型切换后，它可以完全消失。

## 6.3 批处理与调度

GPU 喜欢较大的矩阵运算，用户请求却在不同时间到达、具有不同长度。静态批处理等待整批完成，短请求会被长请求拖住。**连续批处理**允许已完成请求离开，并把新请求插入后续迭代。

调度器需要同时处理：

- 输入长度和预计输出长度；
- 可用 KV cache 块；
- 请求优先级和服务等级目标；
- prefill 与 decode 对计算资源的竞争；
- 取消、超时和客户端断开；
- streaming 返回产生的背压。

某种调度策略提高总吞吐，可能同时恶化单个长请求或低优先级请求的等待。调度结论必须绑定工作负载分布，不能只在单一 batch size 上报告。

## 6.4 量化与低精度

量化把权重或激活从较高精度映射到较少比特。最简单的仿射量化可写成

$$
q=\operatorname{clip}\!\left(\operatorname{round}(x/s)+z,
q_{\min},q_{\max}\right),
\qquad
\widehat x=s(q-z),
$$

其中 $s$ 是尺度，$z$ 是零点。量化减少存储和内存带宽，但误差并不在所有层、通道和任务上均匀。权重量化、激活量化、KV cache 量化和训练时低精度是不同问题；“模型是 4 bit”若不说明对象、分组、校准数据和计算内核，信息不足。

量化验证至少比较任务质量、长上下文稳定性、极端 logit、吞吐、延迟和实际峰值显存。文件变小不保证硬件上更快：若设备缺少对应低精度内核，反量化开销可能抵消收益。

## 6.5 投机解码与多 token 预测

投机解码让一个较便宜的 draft 模型先提出若干 token，再由目标模型批量检查。若接受规则严格按目标分布校正，最终样本仍来自目标模型定义的分布；若实现为了速度采用启发式接受，输出分布可能改变。

收益取决于 draft 速度、候选接受率、验证批量和硬件利用率。语言越可预测，候选越容易被接受；任务频繁转折或目标模型与 draft 差异较大时，额外验证可能得不偿失。多 token 预测头和并行候选树使用不同训练或结构手段，但都试图减少“每个输出 token 必须单独等待一次完整前向”的串行成本。

## 6.6 并行、MoE 与路由

大模型可能无法放入单个加速器。常见并行方式解决不同问题：

| 方式 | 切分对象 | 主要通信 |
| --- | --- | --- |
| tensor parallel | 单层矩阵 | 层内聚合 |
| pipeline parallel | 连续层段 | 阶段间激活 |
| data parallel | 请求或训练样本 | 参数/梯度同步 |
| expert parallel | MoE 专家 | token 路由与 all-to-all |
| context/sequence parallel | 长序列维度 | 注意力所需状态 |

Mixture-of-Experts 让每个 token 只激活部分专家。它可以在不按比例增加单 token 计算的情况下扩大参数容量，但路由不均、跨设备通信和专家热点会限制实际吞吐。总参数量、激活参数量和实际延迟必须分开报告。

## 6.7 Prefill/Decode 分离与缓存复用

prefill 偏计算密集，decode 常偏内存带宽和调度密集，因此服务系统可以把两者放到不同资源池。分离部署需要传输 KV cache，并处理模型版本、精度、位置编码和缓存格式兼容；它不是免费的架构优化。

共享系统提示、长文档前缀或多分支生成还可以复用前缀缓存。合法复用要求 token 序列、模型工件、位置和相关推理配置一致。仅凭可见文本相同不足以复用，因为模板、特殊 token 或适配器可能不同。

## 6.8 服务系统改变了什么

服务层通常不改变模型权重，却会改变用户实际接触的系统：

- 截断策略决定哪些输入进入模型；
- 动态 batch 和低精度内核可能带来数值差异；
- 超时和长度上限改变可完成任务；
- 路由决定调用哪个模型或 adapter；
- 缓存决定哪些中间结果被复用；
- 内容策略和工具运行时决定哪些候选输出可以离开系统。

因此要区分模型能力、某个推理配置下的能力和在线服务能力。卷二将把其中一次请求展开为逐步执行；卷三再说明哪些变化应使用概率语言描述。

## 6.9 最小工程检查

部署一个模型前，至少固定：

1. 模型、tokenizer、adapter 和量化工件；
2. 上下文与输出长度范围；
3. prefill/decode 调度和并行拓扑；
4. 采样、停止和超时规则；
5. TTFT、TPOT、吞吐、P95/P99 延迟和成本口径；
6. 质量回归集与失败恢复方式。

这些字段让“这个模型运行得怎样”成为可复查、可比较的工程陈述。
