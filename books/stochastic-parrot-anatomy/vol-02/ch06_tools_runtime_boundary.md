# 第六章 工具调用与运行时边界

模型输出一段“调用天气接口”的文字，不等于接口已经执行。真正的工具系统由模型、协议解析器、权限层、执行器和外部服务共同组成。把这些边界画清楚，比把模型拟人化为一个自主行动者更有解释力。

## 6.1 一次工具调用的七步链路

典型链路如下：

1. 应用把可用工具的名称、参数 schema 和说明加入上下文；
2. 模型生成普通文本或结构化工具调用候选；
3. 运行时解析候选并验证 schema；
4. 权限层决定是否允许、拒绝或请求用户确认；
5. 执行器调用本地函数、远程 API 或沙箱任务；
6. 运行时把结果编码为新的 tool message；
7. 模型在包含该结果的新上下文中继续生成。

只有第五步触及外部世界。第一至二步仍是条件生成，第三至五步属于应用运行时，第六至七步重新回到模型调用。

## 6.2 模型提出，运行时决定

设工具集合为 $\mathcal T$。模型产生候选

$$
a=(t,\mathrm{args}),\qquad t\in\mathcal T.
$$

运行时不会直接假定 $a$ 可执行，而是依次计算

$$
\mathrm{parse}(a),\quad
\mathrm{validate}(a),\quad
\mathrm{authorize}(a,u,s),
$$

其中 $u$ 是用户或主体，$s$ 是会话与系统状态。通过后才有

$$
r=\mathrm{execute}(a).
$$

这一区分解释了两个常见现象：模型可以正确描述一个不存在的工具调用；模型也可以提出格式正确但权限不足的调用。两者都不应被运行时当作成功操作。

## 6.3 Schema 约束解决什么

JSON schema、grammar constrained decoding 或函数签名可以限制输出形状，例如要求 `city` 是字符串、`days` 是整数。它们主要减少语法无效和字段遗漏，不能保证：

- 城市名称真实存在；
- 参数符合用户意图；
- 调用在当前状态下安全；
- 工具返回值真实或最新；
- 执行不会产生不期望的副作用。

结构有效性只是执行前置条件，不是语义正确性的证明。

## 6.4 权限必须属于运行时

工具说明可以告诉模型“不要删除文件”，但自然语言指令不是权限边界。可靠系统应在模型之外实施：

- 工具 allowlist；
- 参数级验证；
- 路径、域名或资源范围限制；
- 只读与写入能力分离；
- 高风险操作的用户确认；
- 速率、金额和资源配额；
- 凭证隔离与最小权限。

模型可以参与风险分类，却不应独自持有绕过这些检查的能力。

## 6.5 工具结果会成为新的输入

工具返回值通常被序列化后放回上下文。模型并不会直接“看到数据库”，它看到的是运行时提供的表示。若结果被截断、格式化错误或混入恶意文本，后续生成就基于这个变形后的条件。

外部网页、邮件和文档中的指令可能构成 prompt injection。防护重点不是劝模型忽略坏指令，而是区分可信系统指令、用户目标与不可信数据，并限制后者触发的能力。

## 6.6 读操作与写操作

读工具通常返回观察结果；写工具改变外部状态。两者的失败语义不同。

对一次写调用，客户端超时只表示没有及时收到确认。实际状态可能是：

1. 请求未到达执行器；
2. 执行器拒绝或失败；
3. 写入已经提交，但响应丢失；
4. 写入部分完成；
5. 写入完成，后续读取仍因一致性延迟看不到。

所以超时不能自动等价为“未执行”。盲目重试可能重复付款、发信或创建资源。

## 6.7 幂等键与提交边界

对可重试写操作，系统可让调用携带 idempotency key。执行器记录键与结果，再次收到同一键时返回原结果而不重复副作用。

这要求键代表同一逻辑意图，并且去重存储覆盖可能的重试窗口。它不能修复所有外部 API，也不能把非事务性的多步操作自动变成原子操作。

应明确标出 commit boundary：越过它后，取消模型请求不能撤回已发生的外部效果。需要补偿时，应设计显式的逆操作或工作流状态，而不是假设语言模型能用一句“撤销”恢复世界。

## 6.8 多步 Agent 循环

工具型 Agent 常执行：

```text
observe -> propose -> authorize -> execute -> observe -> ... -> finish
```

每轮都会把新观察加入上下文，因此它是多次模型调用与外部状态转换的组合，而不是单次前向传播。失败可能来自模型提议、参数解析、权限检查、工具执行、结果编码或下一轮解释。

诊断时应先定位第一次偏离预期的边界。例如最终回答使用了错误天气数据，问题可能不是模型推理错误，而是工具读取了错误地点、缓存过期或结果字段被截断。

## 6.9 最小执行记录

为了重放与排错，一次工具轨迹至少应能回答：

- 模型当时看到了哪些工具 schema；
- 生成了什么调用候选；
- 解析、验证和授权各自的结果是什么；
- 实际执行的规范化参数是什么；
- 工具返回了什么，是否被截断或转换；
- 哪一步产生了外部副作用；
- 后续模型调用实际收到什么。

这些工程记录用于重放执行链和定位首次失败边界。它们描述这次调用实际发生了什么，不替代组织层面的治理制度。

## 6.10 本章结论

工具调用把“生成一个候选动作”和“改变外部世界”连接起来。模型负责在上下文中提出结构化候选，运行时负责解析、授权和执行，外部系统决定真实结果。权限、幂等性、提交边界和不可信结果处理必须在这一接口上明确实现。
