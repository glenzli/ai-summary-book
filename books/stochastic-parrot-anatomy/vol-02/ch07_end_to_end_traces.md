# 第七章 三条完整执行轨迹

本卷最后不再引入新的抽象，而是把前六章压缩成三条可以逐步追踪的执行轨迹。每条轨迹都区分：用户可见内容、模型内部状态、运行时状态和外部世界。

## 7.1 轨迹一：普通文本回答

用户发送：

> 请用一句话解释为什么天空通常呈蓝色。

### 阶段 A：请求构造

1. 客户端发送消息和解码参数；
2. 服务端选择模型快照与 tokenizer；
3. chat template 加入角色标记；
4. 系统消息、历史消息和本轮消息被拼成实际上下文；
5. tokenizer 产生 token IDs，超长时按服务策略截断。

此时“用户输入的一句话”已经变成带控制标记和历史信息的 token 序列。若两个客户端使用不同 template，它们即使显示同一句话，模型输入也可能不同。

### 阶段 B：Prefill

6. embedding 查表得到初始残差表示；
7. Transformer 各层对整段输入执行 attention 与 MLP；
8. 每层 key/value 写入缓存；
9. 最后位置的隐藏状态投影为词表 logits。

模型此刻尚未产生整句回答，只得到第一个输出 token 的候选分数。

### 阶段 C：Decode

10. 运行时应用温度、top-p 与禁止项；
11. 采样器选择 token，例如某个表示“因”的 token ID；
12. token 被追加，模型只计算新位置并更新 KV cache；
13. 重复步骤 9–12，逐渐生成后续 token；
14. 增量反分词器把合法文本片段送给客户端。

一次可能的表面输出是：

> 因为大气分子对短波长蓝光的瑞利散射通常强于对长波长红光的散射。

这句话的科学正确性需要与外部知识核对。高 token 概率本身没有完成核对。

### 阶段 D：停止

15. 模型生成 EOS，或服务命中长度/停止串；
16. 调度器释放 KV cache；
17. 服务返回停止原因、用量和可选 logprob。

## 7.2 文本轨迹的第一次分歧

若两次输出不同，可按时间顺序检查：

1. 实际模型和 tokenizer 是否相同；
2. 渲染后的输入 token 是否相同；
3. 首步原始 logits 是否相同；
4. logit 处理后分布是否相同；
5. 随机数与选择结果何时第一次不同；
6. 是否仅在反分词或流式展示层不同。

第一处不同通常比最终文本的整体比较更有诊断价值。首 token 一旦改变，后续每一步的条件都改变，最终句子大幅分叉并不奇怪。

## 7.3 轨迹二：文本到图像的潜空间扩散

用户发送：

> 雨夜车站，一把留在长椅上的红伞，纪实摄影。

### 阶段 A：条件与初始状态

1. 文本 tokenizer 和文本编码器产生条件表示 $c$；
2. 系统确定分辨率、采样步数、引导强度和 sampler；
3. 伪随机生成器按 seed 产生初始潜噪声 $z_T$。

这里的 seed 决定初始噪声，但相同 seed 只有在文本编码器、模型、采样器、数值实现和尺寸相同的情况下才具有可比性。

### 阶段 B：迭代去噪

4. 在时间 $t$，去噪网络读取 $z_t$、$t$ 与条件 $c$；
5. classifier-free guidance 组合有条件与无条件预测；
6. sampler 计算 $z_{t-1}$；
7. 重复到既定日程结束。

每一步更新的是整幅图像的潜表示。第 10 步并不对应“已经画完左上角”或“已经决定第 10 个对象”。中间预览只是当前整体状态的解码。

### 阶段 C：解码与返回

8. VAE decoder 把最终潜变量 $z_0$ 转为像素；
9. 后处理可能进行色彩转换、安全检查、缩放或编码；
10. 客户端收到 PNG/JPEG 或对象存储链接。

若输出不符合“红伞”条件，应分别检查文本编码、条件引导、去噪轨迹和后处理，而不能套用自回归文本中的“哪个 token 选错了”。

## 7.4 轨迹三：带工具调用的回答

用户发送：

> 查一下上海明天是否下雨，并给我一句出门建议。

### 阶段 A：第一次模型调用

1. 运行时把天气工具 schema 与用户消息放入上下文；
2. 模型生成候选调用，例如：

```json
{"name":"weather_forecast","arguments":{"city":"上海","date":"tomorrow"}}
```

到这里天气尚未被查询。模型只生成了结构化 token。

### 阶段 B：运行时执行

3. parser 把文本解析为调用对象；
4. schema validator 检查字段与类型；
5. 权限层确认该只读工具允许执行；
6. 执行器把 `tomorrow` 规范化为具体日期和时区；
7. 天气 API 返回结构化预报；
8. 运行时把结果编码为 tool message。

日期规范化必须由运行时明确完成。若服务端时区、用户所在地或请求日期不清楚，“明天”可能被解析成不同日期。

### 阶段 C：第二次模型调用

9. 模型接收原问题、调用记录和工具结果；
10. 它生成自然语言回答；
11. 运行时流式返回并在停止后结束请求。

最终建议的事实基础来自工具结果，措辞来自第二次条件生成。若建议错误，至少要区分：查询参数错误、数据源错误、结果解释错误和表达遗漏。

## 7.5 四层状态表

| 层 | 文本回答 | 扩散图像 | 工具回答 |
|---|---|---|---|
| 用户可见 | 流式文本 | 最终图像/预览 | 工具后的自然语言 |
| 模型状态 | token、隐藏状态、KV cache | 潜噪声、时间条件 | 两次调用各自的 token 与 cache |
| 运行时状态 | batch、sampler、停止规则 | scheduler、seed、VAE | schema、权限、调用状态 |
| 外部世界 | 通常无直接改变 | 通常无直接改变 | API、数据库或设备状态 |

同一个“输出错误”在四层中可能有完全不同的来源。可解释的执行分析必须先确定错误属于哪一层。

## 7.6 本卷给出的解释边界

本卷回答的是：一次输出在机器中如何形成。它没有试图仅凭执行轨迹解决以下问题：

- 为什么训练后形成了当前概率分布；
- 某个内部特征是否对应稳定概念；
- 输出是否真实、公平或负责任；
- 谁对部署后的后果承担制度责任。

这些问题分别需要训练与概率分析、可解释性研究和社会治理框架。把它们全塞进一次 decode trace，只会让生成机制失去焦点。

## 7.7 通向卷三

在三条轨迹中，概率出现在不同位置：文本模型给出词表条件分布，扩散从初始噪声与随机转移中取样，工具系统还叠加了外部数据的不确定性。下一卷不再重复执行步骤，而是追问这些概率从何而来、训练目标怎样塑造它们，以及概率量能解释什么、不能解释什么。
