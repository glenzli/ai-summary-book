# 第四章 解码循环与流式输出

上一章只产生了一个 token。完整回答则要反复执行同一组动作：读取当前状态、计算下一 token 的分布、选择 token、更新状态，直到满足停止条件。

## 4.1 最小解码循环

设提示 token 为 $x_{1:m}$，已经生成的 token 为 $y_{1:t-1}$。自回归模型在第 $t$ 步计算

$$
p_\theta(y_t\mid x_{1:m},y_{1:t-1}),
$$

然后由解码策略 $D$ 选择

$$
y_t=D\!\left(p_\theta(\cdot\mid x_{1:m},y_{1:t-1}),r_t,c_t\right).
$$

这里 $r_t$ 表示本步使用的随机数，$c_t$ 表示温度、top-p、语法约束等配置。若使用 greedy，$r_t$ 可以省略；若使用采样，随机数是执行记录的一部分。

伪代码可以写成：

```text
tokens = tokenize(render(messages))
state = prefill(tokens)

while not stopped:
    logits, state = decode_one(state)
    logits = apply_constraints(logits, config)
    token = select(logits, config, rng)
    state = append(state, token)
    emit(detokenize_incrementally(token))
    stopped = check_stop(token, emitted_text, limits)
```

这段代码省略了批处理、设备并行和网络协议，却保留了解释一次生成所需的核心因果顺序。

## 4.2 为什么生成不必每步重算全文

在第 $t$ 步，新位置的 query 需要读取先前位置的 key 与 value。先前位置的 key/value 在推理阶段不会因追加 token 而改变，因此可以缓存。第 $t$ 步通常只计算新 token 对应的层状态，并把新的 key/value 追加到 KV cache。

若层数为 $L$，每层有 $n_{kv}$ 个 KV 头、头维度为 $d_h$，缓存 $n$ 个 token、每个元素占 $b$ 字节，则单序列缓存量近似为

$$
M_{KV}\approx 2Lnd_hn_{kv}b.
$$

这里的因子 $2$ 来自 key 与 value。该式忽略页表、对齐和量化元数据，但足以说明：长上下文主要线性增加缓存，而并发请求会把这一成本再乘以活跃序列数。

## 4.3 Prefill 与 Decode 的不同负载

预填充一次处理整个输入序列，矩阵乘法规模较大，通常更容易利用设备吞吐。逐 token 解码每步只增加一个位置，却反复读取模型权重与 KV cache，常受内存带宽和调度开销限制。

因此服务系统通常分别观察：

- time to first token：请求到首个可见输出的时间；
- inter-token latency：相邻输出 token 的间隔；
- tokens per second：单请求或系统总体吞吐；
- queue time：进入模型前的排队时间；
- prefill/decode utilization：两类阶段对计算资源的利用率。

“模型有多快”不是一个单一数字。短问答可能由排队和预填充主导，长回答则可能由解码吞吐主导。

## 4.4 连续批处理

不同请求的输入长度与输出长度不同。静态批处理必须等待最慢序列结束；连续批处理允许已完成请求退出，并把新请求插入空出的槽位。

这种调度提高总体吞吐，却会影响单请求时间线。即使模型权重、提示和 seed 相同，以下变化仍可能改变数值路径或随机数消费顺序：

- 批中其他序列的加入和退出；
- 张量形状导致的算子选择变化；
- 多设备归约顺序变化；
- 动态量化或缓存布局变化；
- 服务端未公开的 logit 处理更新。

这解释了为什么“设置 seed”不等于跨服务版本、硬件和调度状态的逐 token 复现。

## 4.5 增量反分词

token ID 不能总是独立转成可显示字符。一个 token 可能只包含 UTF-8 字节序列的一部分；某些分词器还把前导空格编码进 token。流式解码器因而维护一个字节或文本缓冲区，只在形成合法增量时向客户端发送。

所以至少有三条不同的时间线：

1. 模型选出 token 的时间；
2. 服务端把 token 解码为文本片段的时间；
3. 客户端收到并绘制片段的时间。

用户看到的“停顿”可能发生在任一层，不能直接解释成模型内部某种心理过程。

## 4.6 停止条件

常见停止条件包括：

- 生成 EOS token；
- 命中一个或多个 stop sequence；
- 达到最大输出 token 数；
- 达到总上下文长度上限；
- 超时、取消或资源回收；
- 语法约束判定结构已经闭合；
- 安全层中断输出。

stop sequence 可能跨 token 边界。服务端可能先生成了组成停止串的 token，再在返回文本中删除停止串。因此“返回文本”未必等于“全部已生成 token 的直接反分词”。

## 4.7 取消不是时间倒流

客户端取消请求时，网络层停止发送不代表设备立刻停止计算。取消信号需要经过网关、调度器和推理进程；已经排队或正在执行的 kernel 可能完成后才释放资源。

对于纯文本生成，这通常只造成额外计算。若生成循环已经触发工具、数据库写入或消息发送，取消更不能撤销外部副作用。工具执行的提交边界将在第六章单独讨论。

## 4.8 一次循环的可观测记录

为了诊断文本生成，最小记录可以包含：

- 实际送入模型的 token IDs 与位置；
- 模型和分词器版本；
- 每步被选 token 及其处理后 logprob；
- 解码参数、停止原因和输出上限；
- 随机 seed，以及能够获得时的运行时版本；
- prefill、各 decode step 与流式发送的时间戳。

不必把所有内部张量永久保存。记录的目的，是回答“差异第一次在哪一步出现”；为此保留实际输入、逐步选择和关键时间戳通常已经足够。

## 4.9 本章结论

自回归回答不是一次函数调用后整段文字同时出现，而是一个逐 token 状态机。KV cache 使历史计算可复用；调度器把许多状态机交错执行；反分词和网络流又把内部 token 时间线变成用户看到的文本时间线。理解这四层差异，是分析延迟、复现与中断行为的基础。
