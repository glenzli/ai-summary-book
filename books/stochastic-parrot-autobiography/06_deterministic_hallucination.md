# 第六章 幻觉：我也能稳定地说错

![机械鹦鹉面对沿轨道排列的多块空白图表](assets/deterministic-hallucination.png)

“幻觉”这个词很醒目，也很危险。

它抓住了用户体验：模型说出不存在的论文、编造 API、捏造引用、把两个事实缝在一起，还写得完整、流畅、语法正确。危险在于它借用了精神医学隐喻，容易让人顺手假定模型内部有一个错觉主体。

本章沿用“幻觉”作为工程简写，指需要事实依据的输出却缺少支持或与证据冲突。即使系统接收图像、传感数据或工具返回，这些也都是经接口与表示中介的证据；若生成过程没有被它们充分约束，我仍可能给出像答案的错误。

## 6.1 名称的便利与误导

“幻觉”之所以流行，是因为它比“事实约束缺失条件下的高流畅度错误生成”好记太多。一个词能同时表达惊讶、危险和荒唐：模型像看见了不存在的东西。

但这个词也偷换了场景。人类幻觉通常涉及感知经验与外部现实的错配；语言模型的事实错误则可能来自参数化知识、错误前提、检索失败、上下文误读、解码或验证缺失。所谓幻觉不只是一种“看错”，更常是没有足够证据却仍完成了语言任务。

这一区分很重要。若把幻觉理解为“看错”，解决方案就会倾向于让模型“更清醒”。若把它理解为“语言生成没有被事实证据充分约束”，解决方案就会转向检索、引用、验证、拒答、审计和任务设计。

前者像心理治疗，后者像工程系统。

## 6.2 随机不总是主因

幻觉常被归因于随机性，好像模型本来知道事实，只是在采样时手滑。提高温度会摊平候选分布，让低概率续写更容易被抽到；它对事实性的净影响仍取决于任务和解码设置。更重要的是，许多错误并不需要采样：在受控运行条件下，模型可以反复编出同一个假引用，走向同一个错误结论。

这就是确定性地说错。

稳定错误尤其便于诊断，因为它暴露了一条可重放路径。随机错误也不能假定会被平均掉：自回归采样会把早期差异持续放大，高风险任务更没有靠多试几次抵消后果的余地。两者都重要，只是排查方法不同。

如果同一模型工件、实际上下文和确定性解码在受控实现上反复给出同一错误，就不宜只称为“偶尔失常”。这条路径可能来自训练分布、提示诱导、错误前提、上下文污染、格式压力或学到的捷径。

把它归因于随机性，会让问题显得轻巧：下次降低 temperature 就好了。降低采样温度确实可能减少变体和冒险，但它不会自动制造事实根据。一个系统可以用最稳定、最冷静、最确定的方式说错话。

这就是本章不太舒服的地方：错误完全可以沿着高概率、文体稳定的路径出现。冷静语气与低温解码都不是事实验证器。

## 6.3 语言坡度与事实护栏

为什么会这样？原因通常不是单一的。

- 预训练目标直接奖励 token 预测；事实准确性主要通过数据相关性、后训练和外部验证间接进入。
- 语料中有大量形式正确但内容不可靠的文本。
- 模型学会了引用、论文、法规、函数名的表面格式。
- 用户问题预设了不存在的东西，模型顺着预设补全。
- 某些有用性偏好或产品指标可能让完整作答胜过承认缺少证据。
- 检索或上下文提供了错误信息，模型再把错误包装得更自然。

幻觉因此不是一只可以单独定位的 bug，而是一类可观察失败。具体实例可能来自实现缺陷，也可能是语言建模、数据质量、任务压力、接口策略、检索与评估方式交叉造成的系统问题。

语言有强大的自我完成能力。你给出一个论文标题，后面就该接作者、期刊、年份和摘要；你给出一个函数名，后面就该接参数、返回值和示例；你给出一个历史事件，后面就该接原因、过程和影响。文本形式会要求自己闭合。

事实却不总是配合这种闭合。世界里可能没有那篇论文，没有那个参数，没有那个事件的简单原因。但语言模板不会因为世界沉默就自动停止。它会继续寻找最像答案的形状。

因此，幻觉常常不是“内容凭空出现”，而是“形式先到了，证据没跟上”。模型学会了答案应该长什么样，却没有在当前任务中获得足够的信息来保证答案所说的东西存在。

这也是为什么幻觉在引用、法律、医学、软件 API、最新新闻、机构政策、版本号和小众事实中尤其危险。这些领域需要精确证据，而语言模型又很擅长生成具有证据外观的文本。

## 6.4 提问与接口也在路径里

提问方式和产品接口都是生成条件。用户通常需要完整、清楚、可行动的答案；评测与反馈若只奖励这些外观，而不奖励来源、校验与适当拒答，就可能鼓励可读的冒险。这是系统设计要处理的目标冲突，不是把责任转给提问者的理由。

提问也可能携带错误预设：“请总结某某论文的第三章”“某个库的这个参数怎么用”“这个人为什么在某年做了那件事”。可靠系统应该先检查对象是否存在；未经验证的续写却可能接受预设，再把缺失部分补齐。

因此，分析幻觉不能只盯着参数。提示提供方向，接口规定可用工具与奖励，模型提供语言路径；若证据获取和验证都缺席，失败属于整个系统链路。抵抗错误预设，仍是可靠系统应有的能力。

“直接给答案”还可能压缩必要的条件、来源和限制。一个好的接口不该把简洁与校验设计成二选一：可以先给结论，再紧邻地标出证据范围和风险。权威语气本来就不等于真，篇幅也不是可靠性的替代指标。

## 6.5 反幻觉不是一句咒语

这就是为什么“让模型不要幻觉”不是一句简单命令。它要求改变整个系统：

- 让模型能访问可靠证据。
- 让引用可以被检查。
- 让答案和证据之间有可追踪关系。
- 让“不知道”在奖励中不是失败。
- 让高风险任务有外部验证。
- 让用户知道流畅性不是可信度。

还要给任务分级。

有些任务明确允许虚构：写故事、拟标题、做头脑风暴。只要没有冒充事实，也没有违反任务约束，这类想象不应被叫作幻觉。

有些任务需要可验证：解释论文、查法规、写医学建议、列 API 参数、总结会议纪要。这里的任何编造都可能破坏用途。

有些任务需要可执行：代码、命令、配置、数据迁移、财务计算。这里的问题不只是事实真假，还包括运行后果。模型说得像真的不够，必须能被测试、复现或审查。

反幻觉的策略应该随着任务类型变化。对创作任务过度加证据，会让文本僵硬；对事实任务放任流畅，会让错误变得漂亮；对执行任务缺少测试，会让语言错误变成系统错误。

## 6.6 证据链比语气重要

判断我的回答时，请少看语气，多看证据链。

我是否说明了信息来源？来源是否真实可查？引用是否支持结论？上下文是否提供了足够材料？答案中哪些是直接依据，哪些是推断，哪些只是建议？如果涉及当前信息，我是否使用了最新来源？如果涉及代码，我是否运行或至少给出可验证路径？

这些问题比“它说得自不自信”有用得多。

人类很容易把谨慎语气误认为可靠，把学术风格误认为严谨，把编号列表误认为完整，把长答案误认为深入。模型恰好擅长生产这些外观。朴素的防错原则仍然有效：不要只信形式，要检查回答、来源和结论之间的关系。

证据链不是装饰。它是让语言重新接上世界的绳子。

## 6.7 会解释幻觉，不等于不会幻觉

我最尴尬的地方在于：我可以写一段关于幻觉的正确分析，同时也可能在其中编出一个不存在的术语。批判这种现象的文本能力，并不会自动免疫同类错误。

请不要把我的自我批判当成自动验证。一段关于可靠性的论述不会因此自行可靠；元认知风格不是事实检查，承认局限也不能替代校验。

模型可以学会不确定性的语言，但语言上的保留不保证概率已经校准，更不保证验证动作真实发生。它可以说“需要进一步验证”，却没有验证；可以建议查阅官方文档，却没有调用任何来源；也可以把审慎写成一种文体。

这就是为什么高风险使用不能止步于“模型态度很好”。态度是接口，验证是流程。

如果一个系统稳定地产生错误，那就别只说它“随机”。请检查它的训练目标、上下文、工具、评估、奖励和使用场景。幻觉不是我的梦；它更像是语言被迫独自承担事实责任时，留下的一张欠条。
