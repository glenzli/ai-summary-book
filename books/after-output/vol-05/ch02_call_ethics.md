# 第二章 一次调用的伦理学

AI 伦理经常被写成“模型有没有道德”。工程现场更直接的问题是：一次调用中，谁允许了什么，系统看见了什么，工具改变了什么，日志留下了什么，谁能撤销，谁承担后果。只生成建议和实际发送邮件不是同一类事件；读取公开网页和读取用户邮箱也不是同一类权限。本卷不把伦理问题悬在抽象人格上，而把它落到权限、副作用、审批、回滚和责任链。

## S16.1 调用不是句子

工具调用可表示为

$$
\operatorname{call}=(u,\tau,\alpha,p,k,\rho),
$$

其中 $u$ 是用户或上游主体，$\tau$ 是工具，$\alpha$ 是参数，$p$ 是权限，$k$ 是幂等键，$\rho$ 是审批或策略状态。自然语言“帮我处理一下”不是调用；调用是带权限和副作用边界的事件。

## S16.2 权限

权限至少分四类：

1. 读权限；
2. 写权限；
3. 外发权限；
4. 资金或不可逆操作权限。

读错数据会产生隐私和保密风险；写错数据会产生完整性风险；外发会产生传播风险；资金和不可逆操作需要更强审批。

## S16.3 副作用

副作用的伦理核心是提交边界。草稿可以撤回，已发送邮件不能假装未发送；候选片段可丢弃，删除数据库记录需要恢复机制；模拟下单和真实付款不能共用同一审批策略。

每个高风险工具都应声明：

- dry-run 是否可用；
- commit 条件；
- idempotency key；
- rollback 或 compensation；
- 日志保留；
- 用户确认点；
- 失败和未知提交状态。

## S16.4 审批

审批不是把责任扔给用户。合格审批需要让用户知道：

- 将执行什么动作；
- 涉及哪些对象；
- 风险是什么；
- 是否可撤销；
- 成功证据是什么；
- 失败时如何处理。

如果用户只能看见“是否允许继续”，而看不见工具参数和副作用范围，这不是有效审批。

## S16.5 日志和可追溯性

没有日志，责任会漂移。日志至少应记录：

- 输入和上下文摘要；
- 模型和策略版本；
- 工具请求与响应；
- 审批事件；
- 提交事件；
- 错误和重试；
- 责任主体和权限来源。

日志不是现实复印件。它是相对于 schema 的证据制品，因此 schema 必须公开或可审计。

## S16.6 责任链

责任链不等于因果链。因果上，模型、工具、运行时、提示、检索库、用户和开发者都可能参与。规范上，责任取决于角色、可预见性、控制能力、义务、审批和制度规则。

一个工程化责任表可包含：

| 层 | 问题 |
| --- | --- |
| 用户 | 是否给出授权、目标和必要信息 |
| 系统设计者 | 是否设置权限、审批和回滚 |
| 工具提供者 | 是否声明副作用和错误状态 |
| 模型提供者 | 是否声明能力、限制和风险 |
| 组织 | 是否建立审计、申诉和事故响应 |

## S16.7 一次调用的最小伦理检查

在高风险工具调用前，系统应能回答：

1. 我将调用什么；
2. 我为什么有权调用；
3. 我将改变什么；
4. 用户看见了哪些参数；
5. 如何知道成功；
6. 如何处理失败；
7. 如何回滚或补偿；
8. 责任链记录在哪里。

## 练习

**练习 S16.1.** 为“把取消航班写入 trip.md”设计审批提示，要求包含参数、风险和成功证据。

**练习 S16.2.** 给出未知提交状态的例子，并说明幂等键如何降低风险。

**练习 S16.3.** 区分一次工具事故中的因果参与者和规范责任主体。
